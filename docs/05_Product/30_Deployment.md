# ThermoCore
## 30_Deployment.md

**Version:** 1.0  
**Status:** ReadyForImplementation  
**Document Type:** Deployment and operations specification  
**Applies To:** Documentation site, API, Web and later worker services

---

# 1. Purpose

This document defines supported deployment models for ThermoCore.

Initial deployment targets:

```text
Local development
Self-hosted Docker
Linux server
Azure Container Apps
Azure App Service
Kubernetes
GitHub Pages for documentation
```

# 2. Deployment principles

- Linux-compatible;
- configuration through environment and files;
- secrets outside source control;
- repeatable builds;
- health checks;
- structured logs;
- safe database migration;
- independent documentation deployment.

# 3. Service topology

Initial hosted topology:

```text
Reverse proxy
    ↓
ThermoCore.Web / API
    ↓
Simulation job service
    ↓
Database
    ↓
Result storage
```

MVP may combine Web, API and worker in one process for low usage.

# 4. Local mode

Recommended:

```text
SQLite
Local result files
Anonymous access
Single process
```

# 5. Hosted mode

Recommended:

```text
PostgreSQL
Object/blob storage
Authentication
Background job worker
Resource quotas
```

# 6. Container images

Suggested images:

```text
thermocore-web
thermocore-worker
thermocore-docs
```

MVP may use only `thermocore-web`.

# 7. Configuration sources

Priority:

1. command-line where supported;
2. environment variables;
3. environment-specific configuration file;
4. base configuration file;
5. safe defaults.

# 8. Secrets

Examples:

```text
Database connection string
Authentication secret
Storage credentials
Telemetry key
```

Use platform secret stores.

# 9. Database migrations

- run explicitly;
- log migration version;
- back up before destructive migration;
- do not allow uncontrolled concurrent migration;
- support rollback where practical.

# 10. Result storage

Local:

```text
Filesystem under configured directory
```

Hosted:

```text
Blob/object storage
```

Paths shall be generated by the application, not directly from user input.

# 11. Health checks

Endpoints:

```text
/health/live
/health/ready
```

Readiness may check:

```text
Database
Job queue
Result storage
Critical configuration
```

# 12. Logging

Structured JSON logs for hosted deployment.

Include:

```text
Timestamp
Severity
Service
Trace ID
Simulation ID
Event code
```

# 13. Metrics

Recommended:

```text
Active jobs
Queued jobs
Completed jobs
Failed jobs
Simulation duration
Steps per second
Memory usage
Export size
Database latency
```

# 14. Tracing

Distributed tracing may be introduced when Web/API and worker are separated.

# 15. Resource limits

Container or process limits:

```text
CPU
Memory
Concurrent jobs
Job duration
Result size
Upload size
```

# 16. Background jobs

Hosted long-running simulations should use:

```text
Durable queue
Cancellation state
Worker heartbeat
Retry policy
Idempotent job startup
```

# 17. Retry policy

Retry only infrastructure failures.

Do not automatically retry physically invalid configurations or deterministic convergence failures without changing settings.

# 18. Backup

Back up:

```text
Database
Saved configurations
Parameter sets
Calibration data
Result metadata
Optional full result files
```

# 19. Documentation deployment

MkDocs or equivalent may deploy from:

```text
main branch
docs directory
GitHub Actions
GitHub Pages
```

# 20. GitHub Pages workflow

Required stages:

```text
Install documentation dependencies
Build documentation
Validate links
Publish static site
```

# 21. TLS

Hosted deployments require HTTPS.

Terminate at:

```text
Cloud ingress
Reverse proxy
Managed platform
```

# 22. Reverse proxy

Support forwarded headers and base paths.

Do not trust arbitrary forwarded headers from untrusted networks.

# 23. Authentication

Optional for public demo.

Required for persistent private user data.

# 24. Authorization

Users may access only:

```text
Their configurations
Their simulations
Their private exports
Explicitly shared resources
```

# 25. Data retention

Configurable by deployment type.

Example:

```text
Anonymous runs: 7 days
Failed jobs: 14 days
Saved user runs: until deleted
Temporary exports: 24 hours
```

# 26. Security updates

- pin major dependency versions;
- monitor vulnerabilities;
- rebuild images regularly;
- document supported versions;
- publish security policy.

# 27. CI/CD

Pipeline:

1. restore;
2. format check;
3. build;
4. test;
5. documentation validation;
6. image build;
7. vulnerability scan;
8. deploy to staging;
9. smoke tests;
10. production approval.

# 28. Environment names

```text
Development
Test
Staging
Production
```

# 29. Deployment metadata

Expose:

```text
Application version
Build commit
Build timestamp
Environment
Schema version
```

Do not expose secrets.

# 30. Rollback

Rollback strategy shall include:

```text
Previous image
Compatible database schema
Feature flags
Result-format compatibility
```

# 31. Kubernetes extension

Future manifests may include:

```text
Deployment
Service
Ingress
ConfigMap
Secret
Job worker
HorizontalPodAutoscaler
Persistent volume or object storage
```

# 32. Acceptance criteria

Deployment is accepted when:

1. application runs on Linux;
2. secrets are externalized;
3. health checks exist;
4. database migration is controlled;
5. long simulations respect resource limits;
6. logs and metrics identify simulation failures;
7. documentation can deploy independently;
8. backup and retention are documented.
